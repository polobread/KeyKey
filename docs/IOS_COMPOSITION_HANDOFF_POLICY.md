# iOS 組字保留與確認規則

日期：2026-10-23。對應[架構審查](IOS_APP_EXTENSION_HOST_REVIEW.md)的 R01、R02、R04。實作依據仍為程式 commit `c5e04e5c3b2586e9fdf099b9e2bd7c20b43b17f8`；本輪依使用者確認更新產品規則，沒有修改程式、建置或執行功能測試。產品規則已確認，實作方式仍待驗證；以下不是現況已支援的保證，也不是 Apple 強制規定所有輸入法採取的政策。公開 API 的可靠性結論與方案範圍見[鍵盤切換與開闔訊號可行性審查](IOS_KEYBOARD_TRANSITION_API_REVIEW.md)。

依使用者是否真正結束輸入來區分：切到別的鍵盤、明確按「▼」或換輸入框時，只確認已完成文字，取消未完成注音與字根；取消清單或只是開闔、旋轉螢幕時，保留完整組字及未完成輸入。保留後恢復或確認，都以原輸入位置仍可安全操作為前提；位置暫時不明時先停止寫入，確認已失效時才放棄舊編輯責任。

## 五種操作的規則

| 使用者操作 | 已轉出的文字與組字 | 未完成注音或字根 | 回到琦琦時 |
|---|---|---|---|
| 單點地球，確實切到另一個鍵盤 | 在原欄位只安全確認已完成文字一次，結束原組字 | 取消，不輸出原始符號，也不自動猜候選 | 新組字開始，不把舊文字再貼一次 |
| 長按地球開清單，或手指滑出後取消，沒有真的換鍵盤 | 保留組字、已選字結果與候選目標 | 保留原輸入，繼續打完 | 繼續原組字；候選頁面在可能範圍內恢復 |
| 在地球鍵清單選另一個鍵盤 | 與單點確實切換採相同規則 | 取消，不輸出原始符號 | 新組字開始；不能因多一次消失回呼重複確認 |
| 按琦琦「▼」收鍵盤 | 視為明確結束本次輸入，只安全確認已完成文字一次 | 取消，不留在輸入框 | 再點同一欄位也開始新組字，不恢復舊候選 |
| 從欄位 A 換到欄位 B，或切到別的 App | A 仍有效時只確認已完成文字到 A；B 從空組字開始 | 取消；在原位置仍有效時取消自己的未完成標記，不能補送或倒刪到 B | 回 A 時不自動恢復舊組字 |
| Duo 開闔、半開角度改變、內外螢幕切換或旋轉，仍是原輸入位置 | 保留；只調整介面，暫停進行中的按住手勢 | 保留，恢復後接著輸入 | 程序與文字工作階段仍有效才接續；其他情況見下文 |

「保留」不要求保持過時的按鍵座標或手勢。重排後停止退格連發、取消尚未完成的觸控；已完成文字、選字結果與候選目標不能因此改變。候選頁若因顯示容量改變而必須調整，應保留同一候選目標，而不是選入新候選。

## 三個動作各代表什麼

| 動作 | 白話意思 | 可以做什麼與必須避免什麼 |
|---|---|---|
| 保留組字 | 稍後可以接著打、回頭選字 | 保留已完成音節、未完成輸入、已選字結果、候選目標及頁面；不額外送字，不因暫時改版面而學習或確認 |
| 確認組字 | 已完成文字留在原輸入框，琦琦結束這段選字狀態 | 只確認已完成文字一次，取消未完成注音與字根；不是按 Return，不觸發搜尋、傳送或換行；之後不能再用這段舊組字修改文字 |
| 停止沿用舊組字 | 不再假設琦琦還能修改原本的位置 | 保留 App 目前已有的文字，清除或失效化舊本地編輯責任；不在新位置補送、倒刪、清空或重建舊 marked text |

好打觸控目前已把完成文字放進 App 的普通文字中；確認不代表再插入同一份全文。傳統路徑使用 marked text，則需在原位置仍有效時區分已完成文字與未完成讀音／字根，只確認前者、取消後者；不能把含有未完成讀音的整段標記直接確認成普通文字。兩者要有相同的產品結果，但不能共用「把全文再送一次」的想像。[現有文字寫入路徑](../Source/Loaders/iOS-Keyboard/Keyboard/KeyboardViewController.swift#L450)

Apple 的 `unmarkText()` 會留下文字；`setMarkedText` 在沒有既有標記時會作用於目前選取。因此不能把 `unmarkText()` 當成取消未完成輸入；已換欄位或選取後，也不能藉這些 API 追補原組字或取消舊欄位的標記。[文字互動](https://developer.apple.com/documentation/uikit/handling-text-interactions-in-custom-keyboards)、[setMarkedText](https://developer.apple.com/documentation/uikit/uitextdocumentproxy/setmarkedtext(_:selectedrange:))

## 確認時保留哪些內容

採取「已完成文字確認，未完成注音與字根取消」：

- 已完成並轉成文字的部分：保留目前已轉出的組字結果及使用者已選的字；已固定的前段不回頭修改。只有讀音／字根已輸入完整、但仍未轉成文字，不算已完成文字。
- 候選清單已開，但只是翻頁或移動高亮：不把未選入的候選當成使用者已選。確認目前組字結果，結束候選狀態。
- 仍是注音或倉頡／簡易字根的部分：真正切換鍵盤、收鍵盤或換欄位時取消，不輸出原始符號，也不自動選第一個或高亮候選。傳統注音若尚未選字而畫面仍是讀音，同樣取消。取消範圍只限琦琦在原位置仍能安全辨認的未完成輸入，不得刪除已完成文字或 App 的其他內容。
- 只是取消地球清單或開闔螢幕：完整組字、未完成注音與字根都繼續保持可編輯，不確認也不取消。

例如組字區為「你好」加上尚未完成的「ㄕ」，真正切換鍵盤、按「▼」或換欄位時，原欄位只留下「你好」，「ㄕ」取消；如果只有「ㄕ」而沒有已完成文字，就不新增文字。取消清單或單純開闔時，則仍保留「你好」的組字與「ㄕ」，可以接著輸入。

現有 `finishCompositionForInputHandoff` 在好打路徑會嘗試完成讀音，傳統路徑可能選入高亮候選；倉頡／簡易則可能直接清除字根。因此本節不是對現況函式的重新命名，不能直接套用同一函式宣告符合已確認的產品規則。[現有交接函式](../Source/Loaders/iOS-Keyboard/KeyKeyEngine/Sources/KeyKeyEngine/BopomofoEngine.swift#L835)

## 原輸入位置仍有效的判斷界線

保留後恢復或確認前，至少需要核對：仍是原文件、原輸入位置與選取、可修改尾段仍相符、期間沒有未釐清的外部文字變更，且原引擎狀態仍在。這些是安全條件，不是公開 API 已經提供的一把跨程序鎖。

`documentIdentifier` 只區分文件，同一欄位移動游標不一定改變它；UUID 一樣並不足夠。周圍文字恰好相同也不足以證明是同一位置，例如文件內有重複句子。資料為 nil、截斷、互相衝突或仍在重新連線時，應記為未知，不視為已確認相同。[Apple documentIdentifier](https://developer.apple.com/documentation/uikit/uitextdocumentproxy/documentidentifier)、[可取得的文字資訊](https://developer.apple.com/documentation/uikit/handling-text-interactions-in-custom-keyboards)

| 當前情況 | 建議動作 |
|---|---|
| 同文件與位置仍有效，原組字仍在 | 按操作種類保留或確認 |
| 開闔過程連線暫時未知，尚未確認有外部改動 | 暫存組字、停用舊位置寫入；恢復後重新核對，不能直接送出快取操作 |
| 已知換欄位、游標／選取移動、外部修改，或重連後仍無法建立原位置有效性 | 停止沿用舊組字；由目前位置開始新輸入，不補送原本未完成內容 |
| extension 程序已結束、新引擎建立 | 不從 App 現有文字猜回舊組字，不跨程序自動恢復候選或舊刪除責任 |

「停止沿用」可能無法保存尚未送到 App 的注音或字根。這是失去原連線後的能力界線；不能為了補回這些內容，冒險寫進新欄位。App 已接受的完成文字不能因為清除本地狀態而被刪掉。未完成內容若已出現在原欄位的 marked text，應在原位置仍有效時取消；若已失去原連線，不能對新欄位補做刪除。若測試發現舊欄位殘留原始注音或字根，應列為未符合規則的失敗，不能視為允許原樣保留，也不能用改動新欄位來掩蓋。

### R01 不能只靠四分之一秒排除外部變更

建議將自己的待完成文字操作與外部變更分開追蹤；不能因事件發生在 250 毫秒內，就認定它一定由琦琦造成。無法釐清來源時，先停止舊尾段的替換能力。尤其要處理「同一欄位、同一 UUID，但游標已動」的情況。

離開舊文字工作階段後，原先延後的 marked-text 更新、候選操作與刪除要求都必須失效；遲到的操作不能落到新欄位。多次 will／did 通知或重複 appearance 也不能造成重複送字、重複刪除或同一段重複學習。[目前的延後寫入與 guard](../Source/Loaders/iOS-Keyboard/Keyboard/KeyboardViewController.swift#L503)

## R02 地球清單的行為與公開 API 限制

已確認在手指碰到地球鍵、長按開清單或取消時保留完整組字及未完成輸入；真正離開琦琦時，只確認已完成文字並取消未完成注音與字根。`handleInputModeList` 必須繼續保有系統短按與長按清單的行為，不能為了達成文字政策而改成只有單點、移除清單或自行猜測使用者選了哪個鍵盤。[Apple 系統 handler](https://developer.apple.com/documentation/uikit/uiinputviewcontroller/handleinputmodelist(from:with:))

但上述 handler 回傳 `Void`，本次核對的公開介面沒有「清單取消」「選中某鍵盤」專用 completion。普通觸控的結束或取消，也不能直接當成系統鍵盤清單的結果。`viewWillDisappear` 更不能單獨證明發生真正切換。[公開 SDK 宣告](IOS_APP_EXTENSION_HOST_APPLE_SOURCES.md#本機工具與-sdk-凍結)、[viewWillDisappear](https://developer.apple.com/documentation/uikit/uiviewcontroller/viewwilldisappear(_:))

因此，「取消保留」與「真正切換時只確認已完成文字、取消未完成輸入」是已確認的產品結果，目前沒有已驗證的公開 API 接法可在所有情況同時保證。

本輪已核對模式變更通知、iOS 26 型別化訊息、extension 活動通知與 hinge 宣告；它們未提供完整的清單結果與事前交接保證。可控命令、多來源觀測及未完成碼只存鍵盤內等部分方案，詳見[可行方案與適用範圍](IOS_KEYBOARD_TRANSITION_API_REVIEW.md#可行方案與適用範圍)。

開發前須先確認是否能在原位置仍有效時辨認交接；不能假設等知道已換鍵盤，再呼叫 proxy 就必定仍能寫回原位置。這項缺口未解前，不以另加延遲、自訂手勢或清單消失當成答案，也不宣稱本政策能修復 SIGABRT。若原位置已失效，仍讓使用者使用系統切換功能，不為補送舊文字而攔下切換。

## R04 消失與開闔的處理

- **主動按「▼」：** 先依可確認的原位置只確認已完成文字、取消未完成注音與字根，再要求收鍵盤；同一段只確認一次。若原位置已失效或無法核對，仍尊重使用者的收起要求，停止沿用舊組字而不補送到不明位置。排到下一次 main loop 不等於 App 已接受文字，須以後續驗證確認結果。[Apple dismissKeyboard](https://developer.apple.com/documentation/uikit/uiinputviewcontroller/dismisskeyboard())
- **單純版面或開闔：** 暫停手勢、更新版面，保留語意狀態；不能因收到 appearance、layout 或 safe-area 更新就確認、猜字或重建引擎。Duo HIG 建議跨顯示器保持功能與狀態，但沒有承諾 keyboard extension 程序一定存活。[Duo HIG](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo)、[鍵盤程序](https://developer.apple.com/documentation/uikit/creating-a-custom-keyboard)
- **只收到消失通知，原因未知：** 先暫停、保留仍在記憶體內的狀態，禁止對不明位置寫入；稍後若證實同一文字工作階段仍有效才恢復，否則停止沿用。不能把未知一律當成取消、切換或開闔成功。
- **已換欄位或程序重建：** 依新工作階段處理。能在離開前安全確認是理想結果，不代表 Apple 保證每次都會提供最後一次提交機會。不能讓輸入測試頁面先幫忙提交，再把它當成任意 App 都可成功的證據。

Apple 允許在 `viewWillDisappear` 提交編輯，因此該 callback 本身不是誤用；它也沒有定義本案的全部交接原因。鍵盤隱藏不保證程序結束，程序可能存活也不保證一定不被終止。無法因此承諾跨終止恢復完整組字。[Apple viewWillDisappear](https://developer.apple.com/documentation/uikit/uiviewcontroller/viewwilldisappear(_:))、[Custom keyboard](https://developer.apple.com/documentation/uikit/creating-a-custom-keyboard)

## 開發獲准後才執行的驗證案例

以下是政策的驗收條件，這輪沒有執行：

| 案例 | 必須證明的結果 |
|---|---|
| 「你好」加未完成「ㄕ」，長按地球後取消 | 組字仍可改，繼續輸入能完成讀音；文字不多一份，候選目標未被偷換 |
| 句中已選字、翻頁後取消地球清單 | 原已選字與候選目標保持；不把高亮候選當成已選入 |
| 「你好」加未完成「ㄕ」，單點或清單確實換鍵盤，再切回 | 原欄位只留下「你好」一次，沒有「ㄕ」或自動猜出的候選；目標鍵盤能輸入；回琦琦從新組字開始 |
| 「你好」加未完成「ㄕ」，按「▼」後再點同一欄位 | 原欄位只留下「你好」，「ㄕ」取消；沒有送出／換行；舊候選與未完成碼不復活 |
| A 欄組字時切 B 欄，包括兩欄文字一樣或 B 是密碼欄 | A 只留下已完成文字，未完成注音／字根取消；B 不出現 A 的尾段、注音或刪除；回 A 不重複送字 |
| 只有未完成注音／字根，真正切換、收起或換欄位 | 不新增原始符號，不自動選候選；原位置的未完成標記取消；不修改新位置 |
| 打字後 250 毫秒內移游標，並延後送達通知 | 不在新游標位置重播舊替換；是否同一 UUID 都要處理 |
| 閉合到半開再全開、反向切換及旋轉，原位置不變 | 仍存活且可驗證的工作階段完整保留，包括未完成注音與字根；只重排介面；不因重複回呼重複確認 |
| 開闔期間換欄位、App 改字或失去連線 | 不盲目恢復；已知失效後停止舊寫入，保留 App 已有文字 |
| 程序重建或回呼重複 | 不宣稱可恢復已丟失的記憶體；不對新欄位重播舊操作；交接不重複 |

測項須分別涵蓋好打觸控的普通文字尾段、傳統注音的 marked text，以及倉頡／簡易字根；不能用同一段「你好」替代所有路徑。系統鍵盤與使用鍵盤的 App 要各自確認，模擬器與真機證據分開。完整環境定義見[既有驗證矩陣](IOS_APP_EXTENSION_HOST_STATE_MATRIX.md#後續驗證方案)。

## 已確認規則與待驗證事項

1. 已確認：取消地球清單與單純開闔保留完整組字、候選狀態及未完成注音／字根；真正換鍵盤、按「▼」或換欄位時結束原組字。
2. 已確認：明確離開時只確認已完成文字，未完成注音與字根取消，不輸出原始符號，也不藉離開動作自動猜字。
3. 安全原則：選取或文件已變、無法核對原位置時停止沿用；不把舊內容補到新位置，也不對新位置取消原欄位的標記。
4. 公開 API 研究結論：目前查閱契約不足以保證任意 App 中都能完整分辨三種事件並及時交接。待補的是[方案適用範圍、程序投遞與交接次序證據](IOS_KEYBOARD_TRANSITION_API_REVIEW.md#下一步需要的證據)；未達成時列為失敗，不私自改回原始符號保留政策。

產品行為已確認，實作與功能驗證尚未獲准開始；既有地球鍵當機根因仍未確定。
